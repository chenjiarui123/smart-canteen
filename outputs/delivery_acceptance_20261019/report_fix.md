# Markdown 报告单位修复

修复日期：2026-10-19（Asia/Shanghai）。

## 缺陷与修复

原报告直接把内部 `pred_qty` 写到“克”单位下。内部克制菜数量按50克份计数，因此同一菜单的 Markdown 数量比页面与下载 CSV 小50倍。低频潜力菜的原始建议试餐量同样没有换算或明确标注售卖单位。报告还将克制菜的内部数量与“份”“个”等数量加总后直接称为“最终总备餐量”，容易被误认为实际可执行的统一数量。

本次只调整网页后端报告展示：

- 克制菜的菜单数量、低频原始建议试餐量均乘50，使用“克”展示；其他售卖单位保持原数量。缺失单位沿用 CSV 默认“份”的口径。
- 单菜行改为“最终备餐量”，明确高频使用预测量，低频使用试餐建议；若开启总需求重新分配，表格显示重新分配后的最终量，另保留“原始建议试餐量”说明。
- 原内部总需求、最终数量合计、守恒结果明确标为“模型参考值”。备餐差值提醒说明采用同一模型参考口径。
- 新增实际备餐分单位表，分别列出各售卖单位下的高频、低频、合计，不把克、份、个混加为实际总量。
- 订单和销售额展示为参考值，说明低频部分是试餐量对应的估计。

## 变更范围

1. `smart_canteen_web/backend/app/report_generator.py`：在由 DataFrame 转出的独立展示记录上做换算和分组；不写回输入。
2. `smart_canteen_web/backend/tests/test_report_display_units.py`：新增2个回归用例。
3. 本修复说明文件。

本修复没有改冻结模型、SDK vendor、内部 `pred_qty`、预测公式、历史写入、数据源或 CSV 导出逻辑。报告新格式在下一次确认并保存菜单时生成，已保存的旧报告不被覆盖。
