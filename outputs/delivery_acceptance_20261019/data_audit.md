## 需保留的交付限制

1. **时效性**：现有销售、天气及校历均截止 2026-06-10，距本次验收日 131 天。可以验证推理及交付链路稳定性，不能据此宣称 2026-10 的需求预测已用最新数据验证。正式投入当前日期使用时，应提供新增真实销售及目标天气／校历；无需重新训练冻结策略。
2. **单位**：A 有 8 道、F 有 2 道菜的历史售卖单位不一致。SDK 默认 strict 模式会拒绝这类快照，旧数据复现需明确使用其已定义的 `legacy_compatibility`。历史单位合并与转换仍需真实业务依据；不能通过改哈希或随意换算消除。
3. **静态食材缺失**：名称、ID、类别、颜色、营养、口味、特征来源均非空，但主要食材分别有 63／53 个空值。现有代码可退回菜名推断，不影响加载；不宜将这部分食材说明作为人工审核过的事实。
4. **共享上下文**：两食堂分别保存销售与菜品库，天气和校历是全局共享资源，来源为四份初始化销售数据的日期聚合。数据隔离应表述为经营历史隔离，不应承诺天气和校历独立维护。

## 本轮报告准确性修复

初次源代码审阅发现：`backend/app/report_generator.py` 的 Markdown 表格直接把 `pred_qty` 输出在“克”单位下，而前端 `frontend/src/utils/displayUnits.js` 与 CSV 导出 `backend/app/history_store.py::_menu_export` 都对同一模型量乘 50。同一克计价菜的 Markdown 数量可能只有页面／CSV 的 1／50。低频“建议试餐量”文本也直接使用模型数量。

本轮已修复报告显示：Markdown 逐菜量与原始试餐建议对“克”乘 50，并按单位单独汇总；原混合数量已明确标注“模型参考值”，不再把它解释为实际备餐总量。仅转换显示副本，没有改动冻结预测或持久化历史的模型数量。专项测试覆盖克、份、个、缺失单位、重分配后试餐量，以及报告和 CSV 一致性。

Web 人工“按总量重新分配”仍沿用单一模型总量预算；SDK 则按售卖单位分别保持预算。这是已有接口差异，不是本轮显示修复升级了冻结分配机制。最终 HTTP 下载、克换算与历史模型量保持结果见 `web_acceptance.json` 和 `web_acceptance.md`。
