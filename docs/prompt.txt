==================================================
二、菜品属性与名称推断
==================================================

使用“菜品名称”关联销售数据和菜品库。

允许进行以下名称标准化：

- 去除首尾空格；
- 合并连续空格；
- 统一全角和半角字符；
- 统一大小写和常见括号。

菜品库属性优先级最高。

当菜品库缺少主要食材，或者需要判断两道菜的食材是否相近时，允许根据菜品名称进行保守推断。

例如：

- 拍黄瓜和麻辣拌黄瓜：主要食材相同；
- 红烧肉和梅菜扣肉：主要食材均属于猪肉；
- 红烧肉、红烧排骨和梅菜扣肉：可视为相近的浓味猪肉类菜品；
- 土豆烧牛肉和酸辣土豆丝虽然都包含土豆，但主要功能不同，不能仅因包含相同词语就判定为完全相同。

名称推断只用于菜单搭配，不得写回或覆盖菜品库属性。

为推断结果记录：

- inferred_main_ingredient；
- ingredient_family；
- inference_confidence；
- attribute_source。

attribute_source 取值：

- library：来自菜品库；
- dish_name：根据菜名推断；
- unknown：无法判断。

只有高置信度推断可以用于强制冲突约束。中等置信度推断只能用于评分惩罚。

无法匹配菜品库的菜品写入：

unmatched_dishes.csv

不得根据测试集建立名称映射或推断规则。

==================================================
四、初始 Baseline
==================================================

首先实现一个可运行的初始策略，作为后续启发式学习的比较基准。

1. 菜单容量

使用相同食堂、相同餐次、相同星期历史实际出菜数量的中位数。

2. 候选菜池

候选菜至少满足以下一项：

- 在相同食堂和餐次历史中出现至少2次；
- 在相同星期有历史出菜记录；
- 属于菜品库中明确标记的主食或必须保留菜品。

排除长期无销量、数据异常或近期重复过多的菜品。

3. 初始单品预测

pred_qty =
0.7 × 近30天平均销量
+ 0.3 × 全历史平均销量

再乘以星期修正因子。

pred_orders 使用相同方式预测。

pred_rev =
0.7 × 近30天平均销售额
+ 0.3 × 全历史平均销售额

再乘以星期修正因子。

以上预测公式仅作为初始 Baseline，不是固定规则。

后续 Code Agent 可以修改：

- 时间窗口；
- 近期和长期权重；
- 星期修正方式；
- 趋势修正；
- 指数平滑；
- 出菜概率修正；
- 食堂和餐次差异化规则；
- 销量、订单和销售额预测公式；
- 缺失数据回退方式。

4. 初始菜品评分

stability = 1 / (1 + revenue_cv)

score =
pred_rev
× stability
× sqrt(offer_probability)
× repeat_penalty

其中：

offer_probability =
该菜历史出菜餐次数 / 可统计餐次数

repeat_penalty 用于降低近期频繁出现菜品的评分。

5. 初始菜单选择

初始版本使用确定性的约束贪心算法，按 score 从高到低选菜，直到达到菜单容量。

后续允许尝试 MILP 或其他可解释的组合优化方法。

==================================================
五、菜单搭配约束
==================================================

菜单搭配同时使用菜品库属性和高置信度的名称推断结果。

默认约束：

1. 同一相似菜分组每餐最多选择1道。

2. 主要食材完全相同的菜品每餐原则上最多选择1道。

例如：

- 拍黄瓜和麻辣拌黄瓜不能同时选择；
- 凉拌茄子和蒜泥茄子不能同时选择。

3. 同一食材大类且菜品功能相近的菜品不能过多。

例如：

- 红烧肉；
- 红烧排骨；
- 梅菜扣肉。

这类浓味猪肉菜每餐最多选择1至2道。

4. 相同制作方法的菜品不能过多。

例如红烧类菜品每餐最多选择2道。

5. 相同口味不能占菜单过高比例。

6. 非主食菜应避免连续多个推荐日出现。

7. 主食、热菜、凉菜等比例约束，只在菜品库存在对应属性时启用。

8. unknown 或低置信度属性不能直接形成强制冲突，只能作为风险提示。

默认参数写入 config.json，例如：

{
  "max_same_main_ingredient": 1,
  "max_same_ingredient_family": 2,
  "max_same_cooking_method": 2,
  "max_same_flavor": 3,
  "max_same_similarity_group": 1,
  "min_confidence_for_hard_constraint": "high",
  "medium_confidence_penalty": 0.8,
  "avoid_consecutive_non_staple": true
}

这些参数允许在启发式学习过程中调整，但必须通过回测验证。

如果使用 MILP，对不允许同时出现的菜品 i、j 添加：

x_i + x_j <= 1

==================================================
六、固定评价指标
==================================================

实现 evaluator.py。

第一次正式实验开始后，不得修改指标定义。

主要指标一：总量 MAPE

按 date、食堂名称、餐次计算：

total_mape =
mean(
    abs(pred_total_qty - actual_total_qty)
    / actual_total_qty
) × 100%

越低越好。

主要指标二：净收益

actual_rev_selected =
推荐菜在验证期对应的实际销售额之和

overpred_rev =
sum(max(0, pred_rev - actual_rev))

net_benefit =
actual_rev_selected
- 0.5 × overpred_rev

越高越好。

辅助指标：

- qty_wmape；
- order_wmape；
- revenue_coverage；
- dish_hit_rate；
- actual_rev_selected；
- overpred_rev；
- repeat_rate；
- same_ingredient_violation_count；
- same_ingredient_family_violation_count；
- same_method_violation_count；
- same_flavor_violation_count；
- similarity_group_violation_count；
- unmatched_dish_count；
- total_constraint_violation_count。

==================================================
七、最佳策略判定
==================================================

total_mape 和 net_benefit 共同作为主要指标。

新策略必须首先满足：

- total_constraint_violation_count = 0；
- 菜单中没有重复菜品；
- 菜品搭配约束全部满足。

在此基础上，满足以下任一条件时保留新策略：

1. net_benefit 提高，且 total_mape 相对恶化不超过2%；

2. total_mape 降低，且 net_benefit 相对恶化不超过2%；

3. total_mape 和 net_benefit 同时改善。

多个策略表现接近时，依次选择：

1. total_mape 更低；
2. net_benefit 更高；
3. overpred_rev 更低；
4. 菜品搭配违规更少；
5. revenue_coverage 更高；
6. 菜品重复率更低；
7. 策略代码更简单。

==================================================
八、训练集和测试集规则
==================================================

所有策略开发和参数调整必须在训练集内部完成。

训练集按日期排序，使用时间序列划分：

- 前段数据用于计算历史统计；
- 后段连续日期作为开发验证区间；
- 不得随机打乱时间。

测试集保持锁定：

- 不得使用测试集选择规则或参数；
- 不得根据测试集结果修改策略；
- 不得针对测试日期或菜品编写特殊规则；
- 最终策略冻结后，只运行一次测试集评估。

==================================================
九、启发式学习循环
==================================================

每轮实验执行：

1. 读取当前最佳策略和历史实验记录；

2. 分析主要失败问题，包括：
   - 总量预测过高或过低；
   - 单品预测错误；
   - 高销售额菜品遗漏；
   - 过度预测严重；
   - 相同主要食材菜品过多；
   - 相同食材大类菜品过多；
   - 相同制作方法菜品过多；
   - 相似菜同时出现；
   - 相同口味占比过高；
   - 菜品重复频率过高；
   - 菜品库匹配或名称推断失败。

3. 提出一个明确且可验证的修改假设；

4. 每轮尽量只修改一个主要机制；

5. 修改预测规则、评分规则、候选池、搭配参数或优化方法；

6. 在训练集内部进行时间序列回测；

7. 计算全部指标；

8. 将结果追加写入 trials.jsonl；

9. 满足最佳策略判定条件时保存新最佳策略；

10. 实验结果下降时回滚，并记录失败原因；

11. 刷新最佳策略后，删除无效规则、冗余参数和重复代码；

12. 持续运行直到达到 MAX_TRIALS。

不得删除失败实验，也不得只报告最优实验。

==================================================
十、允许和禁止的操作
==================================================

允许：

- 滚动均值；
- 指数平滑；
- 星期、月份和季节规律；
- 近期趋势；
- 历史出菜概率；
- 销量和销售额稳定性；
- 参数搜索；
- 贪心算法；
- MILP；
- 可解释规则和状态机；
- 菜品库属性约束；
- 基于菜名的保守食材推断；
- 消融实验。

禁止：

- 训练神经网络；
- 联网查找现成菜单答案；
- 使用未来数据；
- 使用测试集调参；
- 修改真实销量或销售额；
- 修改评价指标以提高结果；
- 修改菜品库原始属性；
- 对含义不明确的菜品强行推断；
- 删除失败实验；
- 针对测试数据硬编码规则；
- 使用 LLM 主观评分替代 evaluator。
